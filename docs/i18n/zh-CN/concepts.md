# 核心概念

ThreadCells 为原生编码智能体终端增加结构。本页一次介绍一个概念，然后说明这些部分如何组合。

## 智能体

**智能体**是一个以提示、角色、配置文件和项目上下文运行的提供商 CLI。它可以检查文件、使用工具、在获授权时编写代码，并返回结果。

智能体不只是模型名称。两个智能体可以使用同一模型，但拥有不同的角色、权限、推理设置和 worktree。

## 终端

**终端**是智能体运行所在、由 tmux 支撑的真实进程环境。它保留原生提供商输出，并允许操作员在关闭浏览器后重新连接。

终端可以退出，而其持久化结果仍然保留。反过来，一个仍存在的终端也不能证明有用的工作仍在推进。

## 会话

**会话**是 ThreadCells 对一组相关智能体运行的持久化生命周期：标识、生命周期、终端、提供商、配置文件、项目、用量和结果关系。**Add Agent** 会将一个终端添加到该精确会话生命周期，而不是根据重复使用的显示名推断归属。会话让 Statistics 和工作流能够对活跃、完成、历史或保留的运行作出判断。

## 项目

**项目**标识工作所属的 Git 仓库。它为会话、worktree 和结果提供 ThreadCells 的稳定范围；它并不取代 Git remote 或仓库权限。

## 管理的 worktree

**管理的 worktree** 是为有界智能体上下文创建的 Git worktree。它让并行工作者可在不同分支上操作，而不编辑同一个检出。

worktree 会减少冲突；它们不是安全沙箱。智能体仍可能访问其操作系统账户能够访问的任何内容。

## 写入者权限

**写入者权限**回答谁可以变更特定工作上下文。ThreadCells 明确保留该所有权，以免两个独立活跃的智能体被意外地视为可以安全地同时写入同一个 worktree。

审查者通常需要读取权限，但不需要写入者权限。执行实现的开发者则需要。

## 提供商

**提供商**将 ThreadCells 连接到原生编码智能体 CLI，例如 Codex 或 Claude Code。三个状态很重要：

1. ThreadCells 包含提供商适配器。
2. 相应 CLI 已为运行时用户安装。
3. 该 CLI 健康且已完成足以启动的认证。

在 Settings 中列出适配器，不代表外部 CLI 已安装。请参阅[提供商](PROVIDERS.md)。

## 配置文件

**配置文件**是可重用的启动策略。它选择提供商/模型和推理级别，提供指令和能力，定义角色，并可约束智能体参与编排的方式。

内置配置文件提供安全且已知的角色。自定义配置文件让操作员无需修改应用代码即可调整这些角色。

## 主管智能体与工作者

**主管智能体**负责一个较大的任务。它可以将该任务拆分为有界任务，发送给工作者，收集其持久化结果，请求审查，并决定任务是否真正完成。

**工作者**或**受委派智能体**负责其中一个有界任务。工作者应将证据报告给其父级；它不能默默决定顶层结果。

```text
Owner
  ↓
Supervisor
  ├── Developer ── implementation result ──┐
  └── Reviewer  ── acceptance result ──────┤
                                           ↓
                              Supervisor incorporates results
                                           ↓
                                  Top-level completion
```

一个**驻留主管智能体**可以在工作者轮次执行时保持可用。即使模型当前未生成输出，它的驻留也会占用一个主管智能体槽位。

## 工作流

**工作流**是某个任务或受委派任务的持久化协调记录。它跟踪谁拥有工作、哪个逻辑输入是当前输入、结果是否已经交付并整合，以及是否需要完成或所有者决定。

提供商/模型轮次完成不等于工作流完成。主管智能体可能完成一轮，在之后收到工作者结果，并继续同一个开放任务。

## 持久化结果

**持久化结果**是受委派工作产生的结构化完成证据。它可包含摘要、变更文件、检查、风险和阻塞项。即使工作者终端之后退役，ThreadCells 仍会存储并交付它。

交付不等于整合。主管智能体只会在实际使用或评估结果后才确认它。

## 所有者关卡

**所有者关卡**会暂停自主继续，因为下一项决定需要人工所有者作出——例如发布、新的外部信任边界、不可逆的破坏性操作，或此前未获授权的产品决定。

普通模型轮次结束或困难的实现步骤都不是所有者关卡。

## 四种容量

ThreadCells 将四种容量限制分开，因为它们约束机器的不同部分。

### 驻留主管智能体

一个顶层主管智能体或所有者保持可用，以接收回调并继续其工作流。驻留不同于活跃模型执行和受委派 Work 容量。

### 提供商执行

模型正在主动生成一轮输出。提供商配额、进程限制和网络活动约束这一类别。

### 工作上下文

受委派的编码上下文当前拥有工作。即使在等待命令或回调时，它也可能持有一个 worktree 和写入者权限。

### 繁重执行

构建、Chromium 运行、大型测试套件或类似昂贵的主机任务会占用一个繁重槽位。CPU、内存和 I/O 压力约束它。

一个驻留主管智能体可以在不使用提供商槽位的情况下等待，一个受委派智能体也可在不使用提供商或繁重槽位的情况下持有 Work 上下文。因此，同时提高所有限制可能会使主机过载，而不会让工作流更快。请参阅[容量与资源模型](RESOURCE_MODEL.md)。

## 完整示例

所有者为一个仓库启动主管智能体。主管智能体为开发者分配一个管理的 worktree 和写入者权限。开发者生成代码时使用一次提供商执行，随后为生产构建使用一个繁重槽位。其持久化结果返回主管智能体。审查者读取 worktree 并报告一个阻塞性回归。主管智能体启动另一轮，要求开发者修正它，整合两个结果，并显式完成工作流。

终端、会话、worktree、工作流和结果彼此分离，因为每一个都有不同的生命周期和需要保留的真实状态。
