# Процесс релиза

Соберите из чистого закоммиченного дерева изолированный локальный кандидат с помощью `scripts/build_local_candidate.py --output <new-directory>`. Он содержит сгенерированные Docs/UI и локальный wheel. Проверьте `SHA256SUMS`, изучите `candidate-manifest.json`, `sbom.cdx.json` и `EVIDENCE.md`, затем выполните документированную чистую установку с новым префиксом. Публикация тега, удалённой ветки, пакета, образа или публичного релиза никогда не является обычным действием реализации.

## Контрольный список релиза

1. Завершите реализацию и одну независимую интегрированную проверку.
2. Запустите целевые тесты и один содержательный контур production-сборки/браузера.
3. Запустите `git diff --check` и аудит публичной поверхности.
4. Закоммитьте точное принятое дерево.
5. Соберите кандидат из этого коммита, а не из worktree с незакоммиченными изменениями.
6. Проверьте манифест, контрольные суммы, SBOM, идентичность сборки, маршруты Docs и чистую установку.
7. Перед локальным продвижением сохраните прежний runtime и резервную копию базы данных.
8. Рассматривайте любой публичный push, тег, пакет, образ или релиз как отдельное действие, одобренное owner.

Свидетельства релиза подтверждают, что было протестировано и упаковано; сами по себе они не одобряют публикацию и не удостоверяют свойства лицензий/безопасности каждой зависимости.

## OCI-дистрибуция релиза

Одобренные опубликованные alpha-релизы также имеют публичный OCI-артефакт дистрибуции в `ghcr.io/iunknown404i/threadcells-release-bundle`. Он содержит проверенный архив релиза, Python wheel, перечни контрольных сумм, манифест кандидата, SBOM и метаданные release-bundle для одного точного тега релиза и ревизии исходного кода.

Этот пакет является набором для дистрибуции, а не Docker-образом или поддерживаемой средой контейнерного развёртывания. После проверки его контрольных сумм используйте обычный процесс установки и развёртывания кандидата; не пытайтесь запустить OCI-артефакт как службу ThreadCells.

`.github/workflows/publish-release-bundle.yml` публикует по одобренному GitHub Release или явному backfill-dispatch. Он принимает только аннотированные теги `v0.X.Y-alpha.N` с существующим недрафтовым prerelease, пересобирает и проверяет точные исходники, помеченные тегом, отказывается заменять несоответствующий тег версии и обновляет только `latest-alpha`. Во время технического preview ThreadCells не публикует неквалифицированный тег `latest`.

## Соглашение о линейке версий

ThreadCells следует обычному порядку prerelease SemVer. Во время alpha-preview `0.1.X` обозначает значимую итерацию продукта, надёжности или документации; `alpha.N` обозначает дополнительные публикации в рамках той же итерации, когда они действительно необходимы.

- `v0.1.0-alpha.1` был первым публичным alpha-релизом.
- `v0.1.0-alpha.2` — неизменяемый опубликованный технический preview.
- `v0.2.0-alpha.1` — объединённая линейка релиза многоязычности и надёжности.
- Более поздняя публикация в той же линейке релиза увеличивает только alpha-последовательность; новый контур продукта осознанно увеличивает семантическую версию.

Никогда не перемещайте существующий тег. Одни лишь изменения управления репозиторием не требуют повышения версии или релиза. Обновляйте все канонические поверхности, содержащие версию, одновременно только тогда, когда следующий значимый контур реализации готов к публикации.
