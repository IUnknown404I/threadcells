# ローカリゼーションガイド

英語は、ThreadCells の公開ドキュメント、ルート README、および製品上の主張における正規の権威です。翻訳では自然な表現に改善できますが、動作の省略や創作、安全境界の弱体化、制限の変更、コマンドの変更はしてはいけません。

## ロケールモデル

リリースロケールは `en`、`ru`、`zh-CN`、`es`、`pt-BR`、`de`、`ja` です。正規 Markdown は `docs/DOCS_MANIFEST.json` が名前を示すソースに残ります。英語以外の各文書は `docs/i18n/LOCALE/SLUG.md` にあり、次を記録します。

```yaml
---
slug: overview
source: docs/OVERVIEW.md
source_sha256: sha256:EXACT_ENGLISH_SOURCE_HASH
---
```

slug、マニフェスト順序、ナビゲーションへの所属はロケール間で共有されます。ロケール固有の Docs マニフェストやレンダラーを別途作成しないでください。

## 翻訳を更新する

1. まず正規の英語文書を更新して承認します。
2. コードや識別子を変更せずに、すべての主張と見出しを翻訳します。
3. 正確な正規ソースバイトから `source_sha256` を更新します。
4. `python3 scripts/validate_localizations.py` を実行します。
5. Web サイトをビルドし、影響を受けるルートをデスクトップ、タブレット、モバイル幅で確認します。

バリデーターは、欠落、古いもの、不明、重複、または不一致の翻訳済み slug を拒否します。サポート対象ロケールが、英語の変更後に古い翻訳を黙って公開してはなりません。

## ロケールを追加する

ロケールを `website/lib/locales.ts` に一度だけ追加し、その完全なランディング／UI メタデータを提供し、各マニフェスト slug に対して 1 つの翻訳済み文書を追加し、ローカライズされた README を追加して、決定的なルート／ブラウザーチェックを拡張します。言語を切り替える際も同じ公開 slug を維持してください。

`fr` や `ko` のような将来のロケール追加は、範囲の限定されたコンテンツ変更にすべきです。別のアプリケーション、マニフェスト、または Docs アーキテクチャを必要としてはいけません。

## 技術テキスト

正規英語ソースが変更されない限り、次はそのまま保持してください。

- fenced code block とシェルコマンド。
- inline code 識別子。
- API パス、構成キー、環境変数、reason code、profile/provider ID、パッケージ名、ファイルパス。
- ThreadCells、Codex、Claude Code、Git、Git worktree、tmux などの製品名およびプロバイダー名。
- Markdown リンク先とメディアパス。

これらの値の周囲にある説明は自然に翻訳してください。開発者向けガイダンスを読みにくくする直訳は避けてください。

## README ファイル

`README.md` は正規の英語です。各ローカライズ済み README は同じセクション構造に従い、同じ証拠へリンクし、コンパクトな 7 言語セレクターで始まります。現在の言語を太字で強調し、他の 6 言語にはリポジトリ相対リンクを使用してください。

## 視覚的な受け入れ

翻訳では行区切りやセクションの高さが同一である必要はありません。階層、読みやすいタイポグラフィ、動作する CTA、メディア、表、コードブロック、ヘッダー／フッターの動作、水平オーバーフローがゼロであることを保持する必要があります。ドイツ語の拡張、ロシア語の折り返し、スペイン語とポルトガル語のナビゲーション、中国語／日本語の改行に特に注意してください。

流暢な開発者向け読者による意味レビューは引き続き必要です。Markdown、ハッシュ、ルート、ブラウザーチェックに合格しても、構造的な鮮度が証明されるだけであり、翻訳品質は証明されません。
